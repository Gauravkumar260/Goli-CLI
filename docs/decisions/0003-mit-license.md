# ADR-0003: MIT License for GOLI-CLI

**Status:** Accepted
**Phase:** P1
**Date:** 2026-07-03

## Context

GOLI-CLI's choice of license affects:

- Whether enterprises can adopt it (no GPL contagion)
- Whether we can fine-tune GLM-5.2 on trajectory logs (model license compatibility)
- Whether contributors can re-use the code in commercial products
- Whether we can be included in OS distributions

The model backend (GLM-5.2) is MIT-licensed. The two main candidate
licenses for the application code are MIT and Apache-2.0.

## Decision

License GOLI-CLI under **MIT** (matching GLM-5.2's license).

Rationale:

1. **License compatibility.** MIT is the most permissive widely-used
   license. It's compatible with GLM-5.2's MIT license, with all the
   dependencies we plan to use (zod, vitest, tsup, ink, react,
   tree-sitter, etc.), and with both open-source and closed-source
   downstream consumers.
2. **Simplicity.** MIT is one paragraph. Apache-2.0 has patent grant
   clauses, contribution agreement requirements, and is longer. For a
   project that wants to maximize adoption, simpler is better.
3. **Trajectory fine-tuning clarity.** Module 5 will fine-tune GLM-5.2
   on trajectory logs collected from agent runs. The trajectory data is
   generated by users; MIT licensing of the agent makes the data
   ownership clear (the user owns their trajectory data; we collect it
   only with consent, per the privacy policy).
4. **No copyleft contamination.** MIT does not require derivative works
   to be open-source. Enterprises can fork and extend without legal
   anxiety.

## Consequences

**Positive:**

- Maximally permissive — enterprises can adopt without legal review.
- Compatible with all our planned dependencies.
- Simple to understand and apply.

**Negative:**

- No explicit patent grant (Apache-2.0 has one). Mitigation: we are
  not aware of any patent claims covering GOLI-CLI's core algorithms;
  if any emerge, we can re-license under Apache-2.0 later (MIT →
  Apache-2.0 is a compatible one-way upgrade).
- No requirement for downstream consumers to share modifications. This
  is intentional (permissive) but means we won't automatically benefit
  from improvements made by enterprise forks. Mitigation: build a
  strong upstream contribution culture (see `CONTRIBUTING.md`).

## Implementation

- `LICENSE` file in repo root — MIT full text + attribution notice
- `package.json` `"license": "MIT"`
- `NOTICE` file with attribution + model backend notice
- SBOM (SPDX format) generated by Syft on every CI run, with MIT
  license for all first-party code
